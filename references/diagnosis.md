# 先解释损失，再决定改哪里

**简体中文** | [English](en/diagnosis.md)

默认入口是使用者当前问题，不是某个算法。只完成足以作出下一项决定的诊断；已有定位就直接验证，不重复走完本页。

## 1. 把评价与实际代码接起来

从当前工程找出与问题有关的调用点，记到已有日志中即可：

| 要明确的关系 | 从哪里找依据 |
| --- | --- |
| 什么损失实际影响目标，什么只是辅助现象 | 评测器、主指标和硬约束。未完成、晚到、等待可能重叠，不直接相加；没有计分规则就不换算分数。 |
| 计划描述什么时刻、方向与占用 | 计划接口和路径消费者。明确 tick 的前后阶段、速度/区间语义及目标是否继续占用。 |
| 计划怎样变成实际动作 | 动作转换、状态更新与控制调用点。计划与实际只比较同一时刻、同一语义下的字段。 |
| 失败后什么会改变后续计划 | 当前工程的故障处理、修复入口与共享状态。不假设它必须具有某种算法架构。 |
| 哪段计算值得优化 | 已有计时或最小剖析；区分规划计算、仿真、日志及框架开销。不要凭代码长度猜瓶颈。 |

输出具体的使用者文件/函数和已核实关系，而不是通用架构图。工具无法从轨迹猜出应该修改哪个函数；这个对应由 agent 阅读当前工程完成。

## 2. 选一个影响目标的片段

优先检查当前报错、违反硬约束的轨迹，或真实目标中损失明显的实例。若只有汇总量，先找一项可追溯的逐例结果。不要默认把整套 benchmark 重跑一遍。

区分三类陈述：

- **观察**：来自代码、状态或实际计分，例如某一时刻首次与计划不一致。
- **解释**：对观察的候选原因，例如动作映射可能使用了错误的方向。
- **已验证修复**：改动后原失败片段在相同语义下通过相关检查；证据范围仍限于受测行为。

先寻找最早能解释后续异常的分歧，不先优化最后看到的拥堵结果。最早记录到的分歧也可能晚于真正起因；若片段开始时系统已异常，应向前补相关状态。

## 3. 根据证据选择调查分支

| 看到的证据 | 首先核实什么 | 决定可能落在哪一层 |
| --- | --- | --- |
| 同一时刻计划与实际位置、方向或占用不同 | 时钟是否对齐、计划是否已被替换、动作与状态转换是否一致 | 先定位计划消费者或状态更新。对应 C5；映射错误未排除前，不急于换搜索方法。 |
| 明确的等待依赖持续出现 | 阻挡者、预约/占用来源、已知解除事件、可用转移；等待链是否包含片段外参与者 | 当前用户的协调、修复或约束维护。环只是线索，不等于死锁；按证据选 C2、C3 或 C5。 |
| 计划本身无效、缺失或候选被拒绝 | 接口规则、可行转移、拒绝原因、输入是否完整 | 对应规划/约束检查位置；“未找到”不证明无解，也不能仅据此增加搜索预算。 |
| 搜索停滞或检查机会集中 | 实际访问状态、接受记录、最好解返回值、候选覆盖 | 用 C1 或 C6 分支判断先修状态/返回逻辑，还是改变搜索选择。 |
| 小改动在弱起点有效，当前系统没有明显增益 | 是否从同一成熟状态比较，以及该能力是否仍有待解决对象 | C2；先确认追加价值，再考虑替换或放弃，不重复装入同类能力。 |
| 汇总改善与评价排序不一致 | 版本、逐例损失、聚合规则及计分边界 | C4；修正版本选择依据，不能拿工具统计代替实际目标。 |
| 运行时间是主要损失 | 有代表性的实际计时、重复构建量和异常恢复行为 | C3 或当前真正的热点；检查局部收益能否影响目标，避免优化占比很小的部分。 |

仅因位置未变，不能推断列车浪费了一个时间步：慢车可能仍在单元内推进，等待也可能是满足约束所必需。工具中的静止观察数、环数与冲突数不是评分损失分解。

只有规则或有依据的界能证明的部分，才称为当前条件下不可避免的损失。其余标为“尚未解释”。不要把未解释部分自动视为算法可消除的空间，或把目前无改进视为理论极限。

## 4. 将判断落实为一个改动

选中相关 [决策案例](reasoning-cases.md) 后，写清：观察支持哪个分支、哪个事实会推翻它、应检查或修改的用户函数。没有匹配案例就从当前证据推理，不必凑成六类之一。

优先处理影响硬约束且能定位的错误；其余方向根据主目标的损失、证据强度、修改范围与验证成本取舍。不做看似精确却无依据的收益打分，也不同时铺开多个方向。

若缺少证据，只补会改变决定的最小观测，例如一个失败时刻的计划、动作、实际状态及阻挡原因。复用现有日志，或加一处可撤销的观察点；不要先建立全量遥测系统。观测对运行开销或行为可能有影响时，说明其范围。

默认决定可以很短：

```text
问题与依据：<运行/片段/时刻/对象；直接观察与候选解释>
改动位置与理由：<用户文件/函数；为何此处影响目标，或当前只补哪项观测>
确认与去留：<最小检查、实际结果；当前候选/最好版本；未证实部分与下一步>
```

## 5. 用片段确认，不扩大主张

已有原生复现入口就直接使用；否则按 [工具协议](tooling.md) 适配当前日志与回放入口。先验证字段含义、时钟及片段完整性，再相信诊断输出。

- `diagnose` 定位记录中的分歧、声明语义下的冲突和显式等待关系，帮助挑选检查位置。
- `slice` 缩小阅读范围；它不创建可运行的环境状态，也不自动恢复外部列车或随机状态。
- `replay` 通过显式指定的项目适配器，从真实检查点与动作执行；需要足够的环境、列车、事件和随机状态，位置快照不足以保证复现。
- `reservations` 重放预约事件并核对所提供的观察；没有实际快照时只检查该事件模型内部行为。

公开合成例只演示工具行为。真实项目的规则、适配器或数据不匹配时先处理差异，不将工具成功当作 Flatland 验证通过。

局部修复确认后按 [执行与停止流程](autonomous-research.md) 保存结果。整体性能没有测就保持未确认；只有会改变决定的问题才加测。将新证据反馈给当前诊断，不因最初选择了某张卡片就坚持原解释。
