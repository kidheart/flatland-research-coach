# 自动优化：从目标差距到质量晋级

**简体中文** | [English](en/autonomous-research.md)

本流程用于推进使用者自己的 Flatland 目标。先接手实际代码和成绩，按 [诊断指南](diagnosis.md) 判断现有能力与质量差距，再结合 [算法思想手册](algorithm-playbook.md) 实现和评估。默认由 agent 推进，默认追求当前 benchmark 的 100% / 满分；用户另定目标或限定修复、学习范围时遵循其请求。使用者不必逐轮答题。

## 1. 建立目标与可恢复起点

先检查实际启用的算法、候选生成与接受、执行/修复及评测入口，判断现有方案是简单骨架、部分成熟还是已有强基线；同时读取请求、规则和结果。把下列接手信息写进现有记录即可：

| 内容 | 必须明确的决定 |
| --- | --- |
| 主目标 | 用户未另定时取当前 benchmark 的 100% / 满分，不询问目标选择。核实指标、方向、满分定义；未知公式不自行换算，没有满分定义时补问评价口径。 |
| 当前方案与成绩 | 实际算法和实现能力、最新得分、最好得分、对应版本及逐项/逐例损失；总分不能替代细则。 |
| 硬约束 | 合法动作、占用规则、运行时间或其他真实限制；不能用违反约束换取目标值。 |
| 最好已验证版本 | 可恢复位置、实际结果和证据范围；最新文件不自动是最好版本。 |
| 评测条件 | 数据、环境、版本、入口及相关随机性；区分服务器结果、官方本地指标和自定义代理。 |
| 资源与授权 | 已给的时间、计算和外部执行范围；复用会话授权，不反复索要批准。 |

成绩、评分明细或规则未提供且材料中找不到时，直接用一个紧凑问题索取缺项，例如当前/最好版本得分、逐项或逐例结果、benchmark 的计分方式与限制。不要改问“想优化到多少”，也不要把总分未知写成零分。等待回复时继续不依赖这些答案的源码审查和评测准备；影响目标选择的结论与晋级判断保持待定。已有信息不重复询问，具体提问见 [提问库](question-bank.md)。

根据代码和成绩决定改动幅度：简单方案的协调能力明显不足时，直接构建有实质能力提升的组合候选；成熟方案则围绕现有缺口推进。可将必须配合工作的搜索表示、排序与联合改进一起实现，不把“每轮只能改一个小点”当纪律。

没有指定预算，不代表禁止质量评估：先检查原生运行入口和已有耗时，为成本可估计的代表评估设合理超时后推进。无法估计的昂贵运行或超出授权的资源使用才需要澄清，不自行编造固定的大实验预算。

保留当前最好版本及使用者原有修改，在可恢复的候选上工作。失败时仅撤销本轮自己的改动，或放弃隔离候选。不要默认推荐删除历史、硬重置或强制推送；改写历史须有当前会话对应授权。恢复可靠版本不是停止研究的理由。

## 2. 区分正确性检查与质量证据

用户要求提升解质量或分数时，**冒烟是候选进入评估的门槛，质量比较是接纳优化的必要证据**。纯接口修复可以在相关行为确认后完成其限定任务；若总目标仍是提升质量，该修复只是一个阶段。

| 关口 | 应回答的问题与推进条件 |
| --- | --- |
| 针对性冒烟 | 受影响行为是否符合规则，原失败是否修复，更新/恢复是否可靠？失败就定位原因；通过后，质量候选继续进入真实评估。 |
| 代表质量筛选 | 候选在当前主目标上是否优于有效基线，代价是什么？运行实际候选求解器，选择覆盖目标损失及可能受损情形的代表实例，执行足以体现下游影响的 episode 或原生质量评测。 |
| 候选晋级验证 | 改善能否超出用来开发和筛选的案例？在当前 benchmark 范围内，对有希望的候选使用未参与选择的保留案例或新案例，并覆盖已暴露的回归风险。已用来调方案的数据不能再称为独立验证。没有保留样本时明确证据范围，并通过可用的官方评测或稳定性检查推进；不以必须证明跨 benchmark 泛化为门槛。 |
| 权威目标确认 | 当前结论是否需要官方或服务器证据？比赛分数与达标主张须由相应真实评测支持；无法获得时保存为待确认候选，不编造分数或完成状态。 |

筛选前说明所选案例为什么能观察机制收益及其可能代价，不能只挑已知会改善的例子。策略影响整局时，不能用开局几个动作的成功代替整局结果。固定动作回放可检查执行，但只有实际调用候选规划/修复决策的评估才能检验该策略的质量。

同输入、版本和相关资源条件一致的历史基线可复用，不默认每轮双跑。质量比较采用当前问题需要的资源口径；限时任务按实际限制比较，不同时强制建立固定工作量和固定时间两套矩阵。缺失、失败、超时和逐例退步必须保留，不能只比较成功样本。细则见 [质量评估与比较](quality-evaluation.md)。

允许主动进行有界的参数、算法组合和适用条件试错：先提出少量有差异的候选，例如改变优先级、联合邻域、路线/时序选择或阶段预算，再用实际质量决定保留谁。无需事先证明哪个一定有效；能比较、成本可控且有潜在收益就可以探索。组合改动是一个完整候选，不强制逐模块拆开测试。

不默认展开参数网格、多种子扫描或全组合消融。先进行成本合适的代表比较；出现收益或结果不足以决定时，再补有信息量的评估。无明确改善可拒绝当前候选；“性能未确认”不能替代用户要求的质量结论。完整 benchmark 用于确有需要的晋级或目标确认，不机械地每轮重跑。

## 3. 自动迭代循环

1. **更新目标差距。** 读取最好版本的有效结果，列出主要损失、尚未解释部分和当前优先方向。没有程序错误也可以存在规划质量缺口，不只寻找崩溃与轨迹分歧。
2. **选择机制与改动幅度。** 根据 [诊断](diagnosis.md)、[算法思想](algorithm-playbook.md) 和相关 [真实案例](reasoning-cases.md)，定位当前表示、搜索、协调或恢复的局限。决定需要算法骨架升级、联合机制改动，还是参数/预算试验；写明用户代码中将改变的决策、预期收益和可能代价。完整因果解释尚缺时标为探索假设，允许以实测判断。
3. **确定接受标准。** 先写清主目标、硬约束、相关代价和证据要求，再实施。若规则允许某些局部退步换取整体收益，应由真实目标决定；不要事后为候选改标准。
4. **实施、冒烟、筛选。** 修复实现问题后运行真实质量评估，记录实际版本、运行范围、结果和资源。只补决定所需观测，不建立无关遥测体系。
5. **验证并决定晋级。** 有希望的候选完成相应验证后才进入对应证据层的最好版本。保持“本地最好”“权威评测最好”和“待确认候选”的区别，不能用本地收益覆盖已知更好的服务器版本。
6. **更新机制判断，继续剩余目标。** 候选失败时记录失败发生在哪一层，返回损失分析或改换机制；局部成功后看剩余差距。达到目标才按对应证据结束目标工作。

复用 [短记录](experiment-card.md)，重点保留目标变化、质量结果、版本和下一项决定。无须每轮读完全部案例、生成长报告或重复原始输出。

## 4. 失败之后怎样继续

| 结果 | 下一步应改变什么 |
| --- | --- |
| 实现未生效或破坏规则 | 修复接入、状态或约束处理；不把它记成算法思想无效。 |
| 机制生效，代理改善，主目标没有改善 | 检查目标对应、下游执行及预期受益的场景；不能只继续优化代理。 |
| 相关案例改善，另一类退步 | 查适用条件、协调外部影响和资源代价，再决定限制作用范围、改机制或拒绝。 |
| 同等条件下无收益 | 拒绝当前候选，更新解释；根据剩余损失切换机制、组合、参数区域或搜索覆盖。一次设置失败不封禁整个算法家族，也不围绕同一区域无限微调。 |
| 本地改善，权威结果退步 | 先记“退步已观察，原因未知”；核实提交版本、评测条件、逐例损失、约束与预算，再调查场景差异。只有相应证据才讨论过拟合，不能直接据此结束研究。 |

维护一个简短的机制方向表：当前主要损失、已试方向及结果、尚可尝试的不同机制或组合、下一项区分证据。它帮助切换方向，不要求把所有算法都测试一遍。检查是否一直困在同一层：只调在线修复时可转看初始排序与联合规划，只调搜索力度时可转看表达能力、漏访、目标对齐与时间分配。不能用“接受次数增加”“执行了更多测试”替代质量改善，也不能把几次失败或旧注释当成“已经到顶”的证明。

## 5. 分工与停止

独立 agent 只承担具体、有限且能节省工作或提高判断质量的任务，例如检查某个机制的反例、实现隔离候选或审查逐例退步。一个整合者维护目标、最好版本和总预算；不给多个 agent 重复的完整历史，不并行计时相互争用硬件的版本。没有实际独立审查就不声称有。

**拒绝候选、完成一项修复与停止整个优化任务是不同决定。** 目标未达且资源可用时，不能仅凭“没有值得成本的下一步”“我判断预期收益为负”停止。应从尚未解释的损失检查其他机制，或补能决定方向的证据。

整个任务可在目标得到相应证据确认、用户要求停止、真实预算耗尽，或下一项必要工作被具体输入/工具/授权条件阻挡时结束或暂停。当前候选列表用完时，先扩大到不同的机制、组合或算法骨架，或取得能决定方向的观测；列表耗尽本身不是任务停止条件。确实无法继续时，写清已试内容、仍有的替代路线、阻挡下一步的具体条件与恢复方式。保持进取不意味着虚报进展、无限花费或越过用户明确范围。

最后交付：**目标与剩余差距 → 本轮机制及改动 → 实际质量比较 → 候选与最好版本 → 下一步或具体暂停原因**。未达目标就明确未达；局部负结果不证明无解，某 benchmark 达标也不证明普遍最优。宿主结束执行后不宣称仍在后台工作。
