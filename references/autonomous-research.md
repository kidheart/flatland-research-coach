# 自动研究：让 agent 用实验推进优化

**简体中文** | [English](en/autonomous-research.md)

用于使用者自己的 Flatland 工程。这里的问答发生在研究与审查环节，使用者不必逐轮答题。先执行当前授权内能确定的工作，只把影响目标、成本或操作范围且无法从材料中推断的关键问题交给使用者。

## 确立本轮边界

从项目说明、代码、日志和当前请求中核实：工作目录与可修改部分；主要评价指标和硬约束；基线版本与已有证据；可用数据和真实执行入口；时间、计算、实验次数等资源预算。复用现有记录，不要求使用者重新填表。

预算覆盖所有 agent、实验与上下文开销，是上限而非消耗目标。为可能长跑的实验设置实际超时，预留简短分析和保存结果的时间。未给预算时，先做只读核实和成本可估计的短检查；不要自行扩成参数矩阵、全量 A/B 或长跑。无法估计成本且确有必要的长跑才澄清所需预算，不要求使用者为每次冒烟重新批准。

在用户项目中保留可恢复的基线和最好版本；把候选与未验证改动分开。只撤销本轮自己引入的失败候选，不覆盖使用者已有修改。外部提交、推送、分享和收费资源依照当前会话授权处理，不因启用本模式额外要求重复确认，也不凭 skill 自行取得权限。

## 默认短检查，有理由才加测

先选择足以回答当前问题、成本最低的证据。以下是可选层次，不是必须逐层跑完的流水线。

| 检查范围 | 什么时候使用；什么时候止步 |
| --- | --- |
| 已有记录与静态核实 | 先复用版本、数据和环境对应的有效结果。记录已回答问题就不重跑；新改动触及的行为不能用不相干旧结果背书。 |
| 针对性冒烟 | 默认执行受影响路径，优先复用失败小例，检查动作接口、冲突/占用、终点或回滚等与改动有关的条件。成功退出本身不够；相关行为符合预期且无具体新疑点就停止扩大。 |
| 小范围对照 | 只有性能或策略假设影响接纳决定，或冒烟留下具体歧义时才使用。选能区分它的最小代表案例和可比资源；基线结果有效就复用，不默认双跑整个集合。 |
| 更广或完整评测 | 仅用于当前目标需要相应证据、明确要求的检查，或无法由小范围检查解决的具体回归风险。先说明要改变哪个决定、为何小检查不够、成本和停止条件。通过后不为安心重复。 |

不默认做批量 A/B、穷举参数、多种子扫描、全组合消融，或同时跑固定工作量与固定时间两套实验。收益接近噪声时，可以保留“性能未确认”并停测；只有确认该收益值得投入且会影响选择，才做有界复测。

冒烟可支持“受测路径正常”或“该失败已修复”，不能支持“整体更快、分数更高”。将当前可用候选与性能最好已验证版本分开保留；缺少性能证据不阻止完成有针对性验证的修复，但也不升级性能结论。无新改动、新失败或明确未解问题，不重复检查。

## 用真实案例选择调查方向

先从 [脱敏思考案例](reasoning-cases.md) 的索引定位相关段落，不通读全部案例或两种语言。简记相似条件、关键差异和会改变判断的检查。案例中的对照建议按上面的加测条件选用，不自动变成实验任务，也不把曾经有效的方向一起装进项目。

例如，候选只在弱初始解上显得有效时，先与当前成熟基线比较；内部总量和真实评价排序不一致时，先核查计分与逐例变化；怀疑实现提速时，将相同工作量对照与限时完整执行分开。这些分支来自具体经历，详见案例中的实际观察与结论边界。

## 按需要分工，不能用共识替代证据

| 职责 | 要交付的内容 |
| --- | --- |
| 研究与整合 | 确定当前问题、可检验假设、候选改动和实验合同；维护最好版本与剩余预算，决定下一步。 |
| 反证审查 | 检查可能的混淆因素、反例、约束退步和实验区分力；提出最值得补的检查，而不是要求无限加测。 |
| 实施与评测 | 实现候选，运行指定检查，返回实际版本、原始结果、失败与资源消耗。该职责可由整合 agent 承担。 |

小改动由当前 agent 实施和简短自审，不默认建立三个角色或每轮另起评审。存在真实委派工具且一个独立、有限的任务值得其上下文与协调成本时再分工。只给必要规则、相关差异或结果及预期产物；独立评审尽量不先给“它应该有效”的结论。由一个整合者接纳变化，明确修改范围，避免重复读完整历史或重复验证同一事实。

没有多 agent 工具时，同一 agent 先提案再检查反例，明确标记为单 agent 自审。不要写虚构的“研究员说／审查员说”，也不要声称获得独立验证。审查应导向一个可执行检查或明确的接受/拒绝理由；只有新证据或新问题才需要继续争论。

避免让相互竞争硬件资源的基线和候选计时实验并发。文本审查和独立分析可以并行；实验条件和版本依赖需要保持明确。

## 自动迭代循环

1. **锚定基线。** 复用可核实结果与已有标识，必要时补相关小检查；不默认重跑基线，不把最新文件自动当作最好版本。
2. **形成候选。** 简短说明问题、改动及预期可观察结果。机制研究才补竞争解释；直接修复已定位问题无需编造另一种解释。
3. **选择最小检查。** 明确什么结果会改变去留决定，用已有证据、针对性冒烟或有理由的小对照回答；遵循加测条件。
4. **实施并检查。** 做最小合理改动，运行选定检查，记录实际完成、失败或超时。冒烟通过不自动触发完整评测。
5. **决定去留。** 按预先接受标准和硬约束接纳或拒绝。区分修复已验证、性能未确认与性能改善已验证；只将有相应证据的结果提升为最好版本。拒绝时只撤销本轮改动，保留简短失败记录。
6. **判断是否值得继续。** 下一次检查须有具体未解问题、足以改变决定且成本值得。否则保存状态并停止，不因为有剩余预算就寻找更多测试，也不因一次正收益自动放弃仍有价值的既定目标。

复用 [实验记录卡](experiment-card.md) 的短记录或已有日志，仅机制/性能研究按需展开完整字段。保留版本、检查结果和去留依据即可，不为每次冒烟生成长报告、复述全部案例或重复原始输出。记录 agent 自己的判断，不冒充使用者观点；区分提议、实现、启动、完成和已验证。

## 比较与停止

确需比较时，固定输入、版本和相关随机性，选择能回答问题的工作量或时间口径，不自动两套都跑。因果解释需区分策略、吞吐和机器波动；整体目标主张需要相应执行证据。用过的筛选数据不能再叫“未见验证集”，但不为普通冒烟额外建训练/验证流水线。

当目标得到相应证据确认、预算耗尽、没有值得其成本且能改变决定的下一项检查，或遇到关键输入/工具/权限缺失时，保存状态并停止相应工作。缺少执行工具时只能提供分析与可交接的实验合同，明确标记“未运行”，不能声称已完成自动优化。宿主结束执行后，不宣称还在后台运行；需要持续运行能力时由宿主提供。

交付最好版本及可恢复位置、与基线的实际比较、候选去留记录、耗时和失败、仍未知的部分及停止原因。只有本地证据就报告本地结论，不转换成比赛分数或全局最优性。优化失败也应交付有依据的方向排除和保留的可靠基线。
